# Проблема: распознавание речи на iPhone работает только один раз

Статус: не решена. Обходы из кода не помогают, включая перезагрузку страницы. Режимы 9 и 10
помечены в интерфейсе как «в разработке».

Решение по направлению работ (2026-11-03): **не отправлять записи на бэкенд**.
Серверное распознавание исключено по решению владельца проекта. Предложение из
`docs/backend-ideas.md` не является выбранным направлением; его не реализуем.

## Где используется

Режимы 9 и 10 «Отработка лексики» (`index.html`, раздел «режимы 9 и 10») и кнопка
«Проверить микрофон» в настройках. Распознавание — Web Speech API браузера
(`webkitSpeechRecognition`), `lang = 'el-GR'`, `interimResults = true`, `maxAlternatives = 5`;
на iOS `continuous = false`, на остальных платформах `true`. Кнопку микрофона держат, пока
говорят: `start()` по `pointerdown`, `stop()` через 300 мс после `pointerup`.

## Симптомы

Устройство: iPhone, приложение установлено на экран «Домой» (PWA, `display-mode: standalone`);
в обычном Safari то же самое. iOS 27.1.

1. После запуска приложения первое распознавание работает: iOS спрашивает разрешение на
   микрофон (в PWA — при каждом запуске), речь распознаётся.
2. Все следующие попытки «глухие»: `start` и `audiostart` приходят сразу, индикатор микрофона
   горит, но `speechstart` и `result` не приходят ни во время речи, ни после. Через 2–3 секунды
   приходит `error: aborted`, затем `end`.
3. Работает снова только после перезапуска приложения.

Журналы событий с устройства (миллисекунды от вызова `start()`):

```
mode:reset  gum 50, start 80, audio 80, error:aborted 2784, end 2784
mode:fresh  start 81, audio 81, error:aborted 2320, end 2320
mode:shared start 6, audio 52, error:aborted 2556, end 2556
```

## Что пробовали (не помогло)

| Сборка | Способ | Результат |
|---|---|---|
| 2026-11-03-1 | новый экземпляр на каждую попытку, `continuous = true`, `speechSynthesis.cancel()` перед стартом | только первый раз |
| 2026-11-03-2 | один общий экземпляр, `continuous = false` на iOS, без `cancel()` если озвучка не звучит; не ждём `end` прошлой попытки | только первый раз |
| 2026-11-03-4, `shared` | общий экземпляр | только первый раз |
| 2026-11-03-4, `fresh` | новый экземпляр на каждую попытку, обработчики привязаны к попытке | только первый раз |
| 2026-11-03-4, `reset` | новый экземпляр + перед ним `getUserMedia({audio:true})` с немедленной остановкой дорожек | только первый раз |
| 2026-11-03-5 | перезагрузка страницы (`location.replace`) после каждой попытки с восстановлением состояния из `sessionStorage` | только первый раз после запуска приложения; перезагрузка страницы не помогает (убрано в 2026-11-03-7) |

Озвучка (`speechSynthesis`) и `<audio>`/`<video>` между попытками не использовались.

## Что известно

- **WebKit bug 321436**: «SpeechRecognition stops producing results (no onresult/onerror/onend)
  after an <audio>/<video> element plays, on iOS Safari». Статус NEW, iOS 26/27.
  Комментарий от 2026-10-21 (iOS 27.2, PWA) описывает ровно наш случай без всякого
  воспроизведения звука: первое распознавание после запуска работает, дальше `start` и
  `audiostart` приходят, `speechstart`/`result` нет, при `stop()` — `aborted`
  («No speech detected»). Глухая сессия получает `start` через ~37 мс, рабочая — через ~2 с.
  Помогает только перезапуск приложения. `navigator.audioSession.type = "play-and-record"`
  делает глухими все попытки. В iOS 26.6.x того же приложения проблемы не было — похоже на
  регрессию iOS 27. https://bugs.webkit.org/show_bug.cgi?id=321436
- **WebKit bug 317741**: «Speech recognition microphone source should make sure to keep its
  audio session active while capturing». Исправлен 2026-06-26 (коммит 315887@main), но в какой
  версии iOS это исправление вышло, неизвестно; судя по отчётам на iOS 27.2, проблема остаётся.
  https://bugs.webkit.org/show_bug.cgi?id=317741
- **WebKit bug 317747**: исправлен 2026-07-02 (коммит 316394@main). Наличие этого
  исправления в конкретной версии iOS по странице бага установить нельзя.
  https://bugs.webkit.org/show_bug.cgi?id=317747
- Обсуждение в спецификации закрыто потому, что проблема реализации находится вне
  репозитория спецификации, а не потому, что ошибка исправлена:
  https://github.com/WebAudio/web-speech-api/issues/96
- Ранее приводился пример перезагрузки страницы в другом проекте:
  https://github.com/senoldogann/Dot/pull/575. При проверке 2026-11-03 содержимое PR получить
  не удалось; считать его подтверждением рабочего обхода нельзя.

## Вывод

С высокой вероятностью проблема находится в браузерном распознавании или аудиосессии iOS:
симптомы близки к комментарию в bug 321436, а перезапуски распознавателя и страницы на
проблемном устройстве не помогли. Это сильное совпадение, но не доказательство общей
первопричины. Подтверждённого универсального JS-обхода именно этого сценария в проверенных
источниках не найдено. Повторять уже проверенные обходы без новой гипотезы нецелесообразно.

Оговорка по журналам: в текущем `index.html` функция `micUp()` сама вызывает `abort()` через
2,5 секунды после отпускания кнопки, если попытка ещё не завершена. Аналогичный тайм-аут есть
в `micTestStop()`. Поэтому событие `aborted` само по себе не устанавливает причину сбоя;
важнее отсутствие `speechstart` и `result` до остановки. В дальнейшей диагностике нужно
различать вызовы `stop()`, `abort()`, тайм-аут приложения и ошибки браузера.

Переписывать весь проект для замены распознавания не обязательно: `sayScore()` уже отдельно
сравнивает ожидаемый и распознанный текст, а `sayEvaluate()` передаёт результат в упражнение.
Сравнение слов и подсветку можно сохранить при смене источника текста.

Это вывод по коду, предоставленным журналам и внешним источникам. При этом разборе ошибка
не воспроизводилась на реальном iPhone; альтернативы ниже на проблемном устройстве не проверены.

## Варианты, которые ещё не пробовали

### Локальное распознавание в браузере

Модель, например многоязычный Whisper через WebAssembly/WebGPU, обрабатывает звук на
устройстве. Записи не отправляются на сервер; модель сначала нужно скачать. Это основной
кандидат для сохранения PWA без серверного распознавания, но пока не проверенное решение.

Нужно измерить загрузку модели, расход памяти, задержку и качество на коротких греческих
фразах ученика. Поддержка WebGPU сама по себе не гарантирует работоспособность конкретной
модели на iPhone. Этот путь обходит системный `SpeechRecognition`, но по-прежнему зависит
от захвата звука и ресурсов браузера iOS.
Справка: https://huggingface.co/docs/transformers.js/guides/webgpu

### Диктовка через системную клавиатуру — реализовано, проверяется

Сделано в сборке 2026-11-03-8: в режимах 9 и 10 под кнопкой микрофона есть поле ввода и кнопка
«Проверить» (`sayFormHtml()`, `sayCheckTyped()` в `index.html`). Пользователь переключает
клавиатуру на греческую, нажимает 🎤 на клавиатуре, и текст диктовки попадает в поле; по
«Проверить» или Enter он уходит в то же сравнение `sayEvaluate()`, что и распознанная речь.
Поле очищается после проверки. Кнопка микрофона оставлена: первая попытка после запуска на
iPhone работает, а при исправлении iOS заработает полностью. Сайт не может запустить
диктовку клавиатуры своей кнопкой «держи и говори».

Что проверить на iPhone: появляется ли кнопка диктовки на греческой клавиатуре (диктовка
для греческого должна быть включена в настройках клавиатуры), работает ли она повторно без
перезапуска приложения, не мешает ли открытая клавиатура раскладке экрана, срабатывает ли
клавиша Return как «Проверить».

Повторные попытки на проблемном устройстве ещё нужно проверить. Отсутствие собственного
бэкенда не означает локальную обработку: для конкретного языка и устройства нельзя обещать,
что системная диктовка не использует серверы Apple. Если требование — вообще не передавать
голос за пределы устройства, этот вариант нельзя считать подходящим без отдельной проверки.
Справка: https://support.apple.com/guide/iphone/dictate-text-iph2c0651d2/ios

### Нативный захват и распознавание

Отдельное приложение или нативный модуль в обёртке — см. `docs/native-app.md`. Простая
обёртка сайта с прежним `webkitSpeechRecognition` не заменяет проблемный механизм.
Для `SFSpeechRecognizer` нужно проверить поддержку греческого и распознавания на устройстве;
если `supportsOnDeviceRecognition` возвращает `false`, распознавателю требуется сеть.
Нативный API сам по себе не гарантирует офлайн-работу или устранение наблюдаемого сбоя.
Справка: https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportsondevicerecognition

## Первый проверочный эксперимент

До выбора модели проверить захват звука независимо от `SpeechRecognition` и без отправки
записей на сервер:

1. Сделать 10–20 последовательных записей через `getUserMedia` + `MediaRecorder` на проблемном
   iPhone, отдельно в Safari и установленной PWA, сначала без озвучки между попытками.
2. Локально прослушать записи и убедиться, что каждая содержит слышимую речь, а не только
   непустой файл. Затем повторить серию с озвучкой между попытками.
3. Зафиксировать версию iOS, формат записи, ошибки и номера неудачных попыток. Формат выбирать
   через `MediaRecorder.isTypeSupported()`, не предполагать поддержку только одного кодека.

WebKit официально поддерживает этот способ записи:
https://webkit.org/blog/11353/mediarecorder-api/.
В Safari 18.4 добавлена запись WebM/Opus:
https://webkit.org/blog/16574/webkit-features-in-safari-18-4/.
Но утверждение в `docs/backend-ideas.md`, что запись на iPhone стабильна, пока не подтверждено
таким тестом на проблемном устройстве.

Если захват устойчив, следующий предмет проверки — локальная модель на тех же греческих
записях: скорость, память, правильные и ошибочные ответы. Если захват тоже ломается, замена
одного распознавателя проблему не решит. Сравнение с iOS 26.x при наличии устройства поможет
проверить гипотезу о регрессии, но не является обязательным условием этих экспериментов.
